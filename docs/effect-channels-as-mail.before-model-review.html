Effect Channels as a mail system

A GitHub mention is a letter. Channels supplies the mail-handling rules. Durable Objects supply storage, coordination and a bell to wake the clerk.

Reviewed against the workspace · 1 November 2026 · Source notes below

The actual problem: remembering unfinished work

Receiving a webhook and posting a reply is straightforward. The difficulty starts when the same webhook arrives twice, another comment arrives during a run, the server crashes, or GitHub refuses the finished reply.

Durable Objects give you tools

  • An object identity: calls for the same key reach the same object.
  • Persistent storage and transactions.
  • One scheduled alarm per object, to wake it later.

Channels supplies the conversation rules

  • Recognize duplicate events and save accepted ones.
  • Group messages into turns; hold later turns while one is active.
  • Recover callback work and retry saved replies separately.
  • Connect provider webhooks and agent updates to the right conversation.

A Durable Object can run a queue you write. Channels is the queue and delivery logic already written for conversations. The library uses a DO on Cloudflare, or database adapters elsewhere.

One concrete failure

Priya asks the bot to investigate issue 57. The agent finishes, but GitHub is down. Channels saves the requested answer and retries sending it. It does not need to run the finished callback again just to post that saved answer.

DO storage keeps the record; its alarm wakes the retry. Channels decides what the record means and which action to retry. A DO does not understand “GitHub reply” by itself.

What you still build

Your application decides who may invoke the bot, which commands it accepts, where the agent runs and what it does. Starting a remote job should be safe to repeat, using the delivery ID as its job key. Durable mailbox state does not automatically checkpoint an agent’s execution.

Can I do this without a cloud?

Yes. Run an HTTP server and Postgres yourself. Channels’ SQL adapter saves mailbox state and the engine polls for due work. You operate the server and database; Channels still provides the delivery rules. The memory adapter is useful for local experiments but forgets its state on restart.

For a small bot where lost or duplicate replies are acceptable, you may only need a simple webhook handler. Channels earns its place when reliable turns, retries, handoff or multiple providers matter.

The story of one letter

Priya writes a comment on issue 57. Follow her letter to the reply. Press Play and the story below follows the animation. This is a platform-neutral story, including the optional remote-agent pattern. Dashed orange boxes are capabilities you must supply, hosted or self-managed.

  1. 1

    The letter

    Priya writes "@bot please fix this" on issue 57. GitHub seals it in an envelope and posts it to the town's front door.

    In the library: a webhook arrives.

  2. 2

    The stamp

    A clerk checks the stamp on the envelope. A forged letter goes in the bin.

    In the library: the webhook signature is verified. A bad one fails with WebhookAuthenticationError.

  3. 3

    Filing

    The clerk reads the address: issue 57. Every letter about issue 57 goes into the same PO box. If the same letter comes twice, the clerk ignores the copy. Only after the letter is filed does the clerk hand GitHub a receipt.

    In the library: the mailbox key names the box. Repeat events are skipped. The 2xx comes after the save.

  4. 4

    The PO boxes

    The clerk writes accepted letters into persistent storage, so a process restart does not erase them.

    In the library: the storage adapter saves mailbox state. A hosted or self-managed database provides persistence.

  5. 5

    The bell

    Each box has a bell. When mail is waiting, the bell rings. Where a box cannot ring by itself, the clerk drops a note in the carrier's tray: "come to box 57 at 3:05".

    In the library: due-work processing. The adapter and host connect it to an alarm, a poller, or a queued nudge.

  6. 6

    The carrier

    The carrier arrives. The carrier reserves one bundle for processing. New letters can still be filed, but cannot start another turn while this delivery is active. A retryable failure can run the same bundle again.

    In the library: claim with a renewable lease, batch in mailbox admission order, and retry within the configured attempt limit. A lease is not a lock on arbitrary external side effects.

  7. 7

    The recipient

    The carrier hands the bundle to the recipient. The recipient reads "please fix this".

    In the library: your callback runs, for example onMentioned.

  8. 8

    The courier

    The job is long. The recipient hires a courier in another town, such as a sandbox or a pipeline. The courier gets a tracking id and a key.

    In the library: hand off. The delivery id and its access token go to the remote worker.

  9. 9

    The tracking calls

    The courier phones the tracking desk: "started", "step 2", "done".

    In the library: the delivery API receives progress, plan, messages, and the result over HTTP.

  10. 10

    The reply

    The tracking desk saves the requested output before the clerk sends it to GitHub. If GitHub is down, the clerk retries the saved output. Priya eventually reads the reply on issue 57.

    In the library: Channels translates saved delivery-API output into provider calls and retries output separately from callbacks. A crash after a successful post can still cause a duplicate comment.

Who does what: the library or the platform

Cloudflare is not doing the library's job. effect-channels decides the rules for a letter. The platform only has to keep a few promises. This tab lists those promises with no product names first, then shows who keeps each one.

The actor idea, in the library's words

The actor analogy helps: one conversation owns a mailbox and one active delivery. But a Channels mailbox can be a database record processed by different workers; it need not be a permanently running actor. Its accepted inbox is persisted.

Actor ideaIn effect-channels
Private dataMailbox state tracks waiting events, the active batch, retries and the next due time. Seen-event markers can be separate records; the exact schema depends on the adapter.
AddressThe mailbox key, worked out from the event (for example, issue 57 of one repo).
Messages in a queueAccepted events are persisted and assigned sequence numbers. This order is the order admitted to the mailbox, not a reconstruction of an upstream order if webhooks arrived out of order.
One at a timeA claim with an id and a lease. Only the current claim may change the claimed delivery state. After a lease expires, a retry may start; a stale worker’s external side effects still require care.
Messages can be lost or repeatedSave before the 2xx. Skip an event key already seen. Retry the same bundle after a failure. This is the at-least-once pattern from the notes.
An agent’s result updates its deliveryThe remote worker reports over the delivery API. Its result and output operations are saved against the active delivery. They do not become a new waiting webhook or callback turn.

What this says about Cloudflare

effect-channels alone

  • Dedupe, claim and lease, order, batching and retry rules; their enforcement requires atomic storage from the adapter.
  • The decision of when a box is next due.
  • The delivery API and the hand-off to a courier.

Cloudflare alone

  • Addressing by name (1).
  • Durable storage with transactions (2, 3).
  • A durable timer per box (6).

Durable Objects combine identity, persistent storage and an alarm. Our Cloudflare deployment defines one Worker and two DO classes (mailbox and AgentSession), with many independently running objects. It needs no mailbox poller. A platform without them needs extra parts to fill the same gaps: a nudge queue and a sweep on Azure and AWS, or a poller on a plain database. The rules above do not change.

This integration is at least once: callbacks may repeat, and posting a new comment can repeat after a crash between posting and recording success. Delivery-API output retries are separate from callback retries. Direct provider calls inside a callback remain that callback’s repeatable side effects. AWS and Azure dedup markers have a 30-day TTL, so deduplication is not a forever guarantee.

Is the Durable Object inside the same compute?

Same deployed bundle, separate running instances. Ingress Worker memory is not durable shared state. Calls for one DO identity reach its active instance, with its own persistent storage and alarm; its in-memory state can disappear on restart.

The mailbox’s alarm is owned by Channels. A DO can have one alarm scheduled at a time; Cloudflare supplies bounded retries for a throwing handler, while Channels implements delivery retry policy. The separate AgentSession currently starts a detached echo task and saves no agent checkpoints. Persistent mailbox state does not make that task resumable.

How the story is deployed on AWS

From infra/aws in slop-factory-pieces. Same bot behaviour as the Cloudflare version, built from API Gateway, Lambda, DynamoDB, SQS and EventBridge Scheduler. Deployment status is not established by this review; this explanation checks source, not a live AWS account.

ChapterComponentWhy
1 The letterAPI Gateway HTTP APIOne route: POST /integrations/github/webhook. It passes the request to the Receiver Lambda.
2 The stampReceiver LambdaIt verifies the signature.
3 FilingDynamoDB: one item per issue or PRThe event and its dedup marker are written in one transaction, so a redelivery does nothing a second time.
4 The PO boxesDynamoDB tableDurable. An item is limited to 400 KB, and waiting events carry the full webhook payload.
5 The bellSQS nudge, and an EventBridge SweepThe note is delayed by readyAt - now, capped at 900 s. It is a standard queue because FIFO has no per-message delay. A Sweep every minute re-nudges due boxes.
6 The carrierProcessor LambdaOne message per invocation, 30 s timeout. At most 20 passes, and no new pass after 15 s. Then it nudges again. A failed record is retried, and after 5 receives it goes to the dead-letter queue.
7 The recipientEcho agent, inside the ProcessorIt waits 5 s, then replies.
8 The courierNot connectedHandoff is used inside the Processor, but the delivery API is not exposed through API Gateway. External handoff over HTTP is not exercised.
9 Tracking callsNot connectedThe same reason.
10 The replyGitHub API, from the ProcessorPosting is at least once. GitHub comments have no idempotency key, so a crash can cause a double post.

Settings come from SSM Parameter Store at cold start. Known limit: GitHub does not redeliver a failed webhook by itself, so a failed Receiver response may leave an event unaccepted; an operator must redeliver if it was not saved. A failed response alone does not prove the write never committed.
