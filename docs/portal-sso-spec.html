Technical specification

Entra sign-in with GitHub and Jira connections

A reference design for a company portal. Users sign in with Microsoft Entra ID. Then each user connects a personal GitHub account and a personal Jira account. This document lists every object to create, every setting to choose, and the reason for each choice.

1. Summary

The portal has one identity system and two connectors. Entra ID proves who the user is. GitHub and Atlassian give the portal permission to act for that user on their own systems.

Entra ID: identity

OpenID Connect sign-in. The ID token claim oid becomes the user key in the portal.

GitHub: delegated access

A GitHub App (default) or a GitHub OAuth App. The portal receives a token that acts as the user.

Atlassian: delegated access

An OAuth 2.0 (3LO) app. The portal receives a token that acts as the user in Jira Cloud.

Azure: hosting and trust

A Container App with a managed identity. The identity replaces the Entra client secret.

Design principles

  1. Prove both identities. A user signs in with Entra, then proves ownership of the GitHub and Jira accounts with each provider's own login. No email matching. No admin mapping table.
  2. No more access than the user has. The portal stores user tokens, not a shared service account. A token can only do what the user and the app can both do.
  3. No long-lived secret where a better option exists. Entra trusts the managed identity. Provider secrets stay in Container App secrets. Stored user tokens are encrypted.
  4. One deployment, one mode. Feature flags and conditional Terraform blocks turn each connector on or off without code changes.

5. Managed identity and federated credential

In production, the portal does not hold an Entra client secret. The Container App has a user-assigned managed identity. Entra trusts tokens from that identity as proof that the caller is the app registration.

sequenceDiagram
  autonumber
  participant P as Portal code
  participant M as Managed identity endpoint
  participant E as Entra token endpoint
  P->>M: Request token for audience api://AzureADTokenExchange
  M-->>P: Signed JWT, subject is the identity object ID
  P->>E: POST /oauth2/v2.0/token with auth code and client_assertion
  Note over E: Match issuer, subject and audience
to the federated credential on the app registration
  E-->>P: ID token for the user

Figure 2. Token exchange without a client secret.

Federated credential values

FieldValueReason
Issuerhttps://login.microsoftonline.com/<tenant-id>/v2.0The managed identity token is issued by your own tenant.
SubjectObject (principal) ID of the managed identityOnly this one identity can act as the app. A different identity in the tenant is refused.
Audienceapi://AzureADTokenExchangeThis is the fixed audience that Entra requires for workload identity federation.

Why this choice

No value to leak

The managed identity token lives for a short time and only the platform can issue it. There is no secret in git, in an environment variable, or in Terraform state.

No rotation job

A client secret has an expiry date. When it expires, sign-in stops. A federated credential has no expiry.

Tight scope

The subject field links the app to one identity. You can create one identity per environment (dev, test, production).

Built The code in auth.ts uses two modes. If AZURE_MI_CLIENT_ID is set, it sets the client authentication method to none. It then adds client_assertion to the token request in a custom fetch. If the variable is not set, Auth.js uses the client secret from .env.local.

Limit. GitHub and Atlassian do not accept this kind of federated trust for the user-authorization flow. Their client secrets must stay in Container App secrets (section 10). Microsoft sets a maximum number of federated credentials for each app registration. Check the current limit in Microsoft documentation before you plan many environments.

6. Sign-in flow

The portal uses the OpenID Connect authorization code flow. The code exchange happens on the server.

sequenceDiagram
  autonumber
  actor U as User
  participant B as Browser
  participant P as Portal
  participant E as Entra
  U->>B: Open the portal
  B->>P: GET /
  P-->>B: 302 to Entra authorize endpoint
  B->>E: Authorize request with state and nonce
  E->>U: Sign in, MFA, Conditional Access
  E-->>B: 302 to /api/auth/callback/microsoft-entra-id with code
  B->>P: GET callback with code
  P->>E: Redeem code with client assertion
  E-->>P: ID token with oid, tid, roles
  Note over P: Validate issuer, audience, signature, nonce
Store claims in session
  P-->>B: Set session cookie, 302 to /

Figure 3. Entra sign-in with the authorization code flow.

  • Auth.js sets state, nonce and PKCE for the sign-in request. The portal does not implement these checks. Use the library defaults.
  • AUTH_URL must be the public HTTPS origin. Container Apps terminates TLS in a proxy. Without this value, the callback URL can have the wrong host. Built
  • AUTH_TRUST_HOST=true tells Auth.js to trust the proxy headers. Set it only behind a known proxy. Built
  • AUTH_SECRET signs the session cookie. Use a random 48-character value. Keep it secret (see section 14).
  • The session stores oid and tid. Every connector call reads session.oid on the server. The client cannot choose the user.

Recommendation

Use a GitHub App. It follows the least-privilege principle. A token can only read the repositories where the App is installed, and only with the permissions you set. A stolen token expires in hours. An OAuth App token gives write access to every private repository of the user and has no expiry.

9. Atlassian (Jira)

The portal uses OAuth 2.0 with three-legged authorization (3LO). The portal calls Jira Cloud through api.atlassian.com, not through the site URL.

SettingValueReason
App typeOAuth 2.0 integrationThis type gives user-delegated tokens.
Callback URLhttps://<portal-host>/api/connect/jira/callbackThe console can accept only one URL. Register one app for each environment.
ScopesGranular read scopes for issue search, plus read:me and offline_accessRead-only access is enough to pick an issue. offline_access gives the refresh token. Without it, users must sign in again each hour.
Scope overrideATLASSIAN_SCOPESAtlassian answers 400 if you ask for a scope that the app lacks. Change scopes without a code change.
Authorize parametersaudience=api.atlassian.com, prompt=consentThe audience is required. consent shows the site selection and scope list each time.
Distribution"Sharing" before other people connectIn development status only the owner can authorize the app.
Owner of the appA shared admin or service accountThe same reason as for GitHub: do not tie the app to one person.
  • Refresh tokens rotate. Each refresh returns a new refresh token. The portal must store the new one at once. The code does this. Built
  • One site only. The portal uses the first site from accessible-resources. If your users have more than one Jira site, add a site picker. Risk
  • PKCE. The portal-poc Atlassian flow uses a client secret and does not send PKCE. Verify whether the current Atlassian documentation supports PKCE for 3LO, and enable it if it does.

Interpretation. This section reads "conditional deployment" as conditional Terraform resources and feature flags. If you also meant Microsoft Entra Conditional Access policies, section 7 covers them.

Mode change rule

Changing GITHUB_AUTH_MODE invalidates every stored GitHub connection. Each record keeps the mode that created it. The portal does not use a record from another mode, and the user connects again. Also change the client ID and secret to match the new kind of app.

12. Deployment order

The order matters. The public URL of the portal exists only after the first apply. GitHub and Atlassian need that URL as a callback. The Entra redirect URI needs it too.

Figure 9. Phases of a first deployment.

  • Phase 1 detail. Terraform creates the resource group, the managed identity, the federated credential, the Container App environment and the redirect URIs. The environment default domain gives the URL.
  • Redirect URI list. The azuread_application_redirect_uris resource replaces all redirect URIs of the Web type. Include localhost and the deployed URL in the list. Do not add URIs by hand, because Terraform removes them.
  • Container image. The portal-poc pipeline pushes to GitHub Container Registry. The image must be public because Container Apps pulls it with no credentials. For a company, use Azure Container Registry with the managed identity instead.
  • One command. scripts/deploy.sh builds, pushes, plans, asks for confirmation and applies. scripts/destroy.sh removes the Azure objects and keeps the app registration.

Steps

  1. Choose a name, a region and a subscription. Confirm you can create app registrations in the tenant.
  2. Create the Entra app registration as a single-tenant Web app (section 4). Add yourself and the deployment identity as owners.
  3. Create the enterprise application. Set "Assignment required" to Yes. Create the Portal.User role and assign a group (section 7).
  4. Run terraform apply with the placeholder image. Record portal_url.
  5. Create the GitHub App under your organization (section 8). Install it on the selected repositories.
  6. Create the Atlassian OAuth 2.0 app (section 9). Set the scopes.
  7. Put the client IDs and secrets in the deployment environment. Do not commit them.
  8. Build the image and run terraform apply again.
  9. Add the role check and tenant check to auth.ts (section 7).
  10. Test with an assigned user and with an unassigned user. The unassigned user must be refused.
  11. Test connect and disconnect for each provider. Test token refresh after the access token expires.
  12. Fix the items in section 14 before real users connect.

14. Gaps and open decisions

Known gaps in the proof of concept

GapImpactAction
Risk Token store writes local filesContainer storage is not durable. Tokens are lost on restart or scale-out.Implement the TokenStore interface with Cosmos DB or similar. Keep the AES-GCM layer.
Risk Encryption key is in Terraform stateAnyone who can read the state can read the key.Keep the key in Azure Key Vault. Use remote, encrypted, access-controlled state.
Risk AUTH_SECRET is a plain environment variableIt shows in the Container App configuration.Move it to a Container App secret and reference it.
Risk No access gateAny tenant user can sign in.Do section 7.
Risk Disconnect does not revoke tokensA deleted record leaves a valid token at GitHub or Atlassian.Call each provider's revoke endpoint before you delete.
Risk Refresh is not locked across replicasTwo refreshes can race. Atlassian rotates refresh tokens, so one user can lose the connection.Keep max_replicas = 1 or add a lock in the store.

min_replicas = 0The first sign-in after idle time is slow.Set 1 for production.
Public image on GHCRAnyone can pull the image.Use a private registry with managed identity pull access.
Local Terraform stateNo team access and no locking.Use an Azure Storage backend.

Decisions for your organization

  1. GitHub mode: App (recommended) or OAuth App.
  2. Who owns the GitHub App and the Atlassian app, and who rotates their secrets.
  3. Access group: which Entra group gets Portal.User, and whether you have P1 licences for group assignment.
  4. Conditional Access: MFA only, or MFA and compliant device.
  5. Number of environments (dev, test, production). Each one needs its own redirect URIs, GitHub callback, Atlassian app and managed identity.
  6. Whether Terraform should create the app registration in the future.
  7. Whether the agent later acts as the user (user token) or as the bot with a narrow installation token.
